## Must-fix — still open, verified 2026-07-05

1. **`./gradlew test` red.** ~~`AlgorithmParityTest.kt:25` KDoc text contains `shared/test-vectors/*.json` — Kotlin block comments nest, so that `/*` opens a nested comment that never closes → "Unclosed comment" at line 404.~~ **FIXED 2026-07-05** (commit `c8856c6`, Android repo). Fixing the comment surfaced a real bug underneath: Android's `calculateStreak`/`calculatePartnershipStreak`/`calculateGroupAccountabilityStreak` hardcoded the real wall clock instead of taking an injectable `now: Date`, unlike iOS which already had this. Added the `now` param to match iOS's contract; `./gradlew test` is green.
2. **Security: any authenticated user can join/modify any group.** **FIXED IN CODE 2026-07-18, DEPLOYED WITH A KNOWN GAP** (iOS repo `3660df5`, Android repo `486000c`; rules deployed `74bb8d8`). A rules-only fix (require a `group_invitations` doc to exist before allowing self-join) was attempted first and found forgeable: an attacker can mint their own invitation naming themselves as both `fromUserID` and `toUserID`, satisfying any doc-existence check. Real fix: `groups.memberIDs` can no longer be written by a client at all unless already a member (removed `isSelfJoinOnly()` entirely). Joining now goes through Cloud Functions (admin SDK, bypasses rules): `onGroupInvitationUpdated` and new `onGroupInviteLinkAccepted` (`functions/src/index.ts`) add the joiner only after verifying the *inviter* (or link creator) is a current group member — that membership check, not "the invitee accepted," is the actual authorization boundary. Clients now only write to fields rules already restrict to the caller (invitation status; or the link's `uses`/`acceptedByUserId`/`acceptedAt`/`conversionStatus`, same shape as the pre-existing `onSoloInviteLinkAccepted` pattern) and poll for the Cloud Function to finish. Tried adding `isGroupMember` to `group_invitations` create rule as defense-in-depth, but reverted it (iOS repo `8f0ce52`): groups sync local-first in an un-awaited background task (`LocalFirstGroupRepository.createGroup`), so "create group, then invite members" can hit this write before the group doc exists in Firestore — the check would hard-deny a legitimate invite for no real security gain (the Cloud Function already checks membership at accept time against the by-then-synced group). Also fixed `onGroupInviteLinkAccepted` unconditionally stamping `conversionStatus: "completed"` even when the membership check refused the join (`8f0ce52`) — now stamps `"failed"` with a reason in that case. **Verified against Firestore + Functions emulators** (`@firebase/rules-unit-testing`), 8 scenarios: self-minted-invitation and self-minted-link attacks both confirmed blocked (attacker never lands in `memberIDs`, `conversionStatus` correctly reads `"failed"` not `"completed"`); real accept-invitation and accept-link flows confirmed working end-to-end through the actual Cloud Functions; invitation-create confirmed to still succeed when the target group doc doesn't exist yet (the race case); partnership-accept's `accountabilityPairs` write via `updateGroup` confirmed still works under the tightened `isMember`-only groups update rule. **Pre-existing, flagged not fixed**: `onSoloInviteLinkAccepted` doesn't verify `createdByUserId` actually owns `commitmentId` — same missing-anchor shape as this fix closed elsewhere, out of scope here. Also pre-existing (not a regression — reverting `isGroupMember` from the create rule just restored the original baseline): any authenticated user can still mint a `group_invitations` doc addressed to any victim for any group; harmless because the CF checks the *inviter's* membership at accept time regardless of who created the doc, but noted so it isn't mistaken for something this fix introduced.
   **Cloud Functions deployed 2026-07-18** (`firebase deploy --only functions` — all 16 functions updated/created including new `onGroupInviteLinkAccepted`, succeeded). Safe to deploy alone: the new/extended trigger logic piggybacks on writes that already happen under the *old* client behavior (old clients still write `memberIDs` directly and still flip invitation status / set `acceptedByUserId`), and `addGroupMemberIfInviterIsMember` no-ops if the joiner is already a member — so it's a harmless no-op against every currently-installed client.
   **`firestore.rules` DEPLOYED 2026-07-18 (`74bb8d8`) with `isSelfJoinOnly()` restored as a temporary compatibility path.** Originally held back because deploying `isMember(resource)`-only would break group-join for 100% of currently-installed clients (the new claim-field flow hadn't shipped to either store yet) and no force-update/Remote-Config gate exists on either platform to shield stragglers. Investigated building one — **found it doesn't actually solve this deploy**: a minimum-version gate only runs in builds that already contain it, so it can't retroactively protect clients that predate it (chicken-and-egg). Decision made with the user: keep `isSelfJoinOnly()` alive alongside the CF-mediated path. Updated clients never hit it (they only write fields already restricted to the caller; the real `memberIDs` write happens server-side). Old clients keep working exactly as before. **Net effect: this specific hole (any authenticated user can self-join any group by uid alone) stays open** — remove `isSelfJoinOnly()` once old-client adoption is low enough. The `isValidReactionDelta()` fix (should-fix, non-breaking) ships to everyone immediately as part of the same deploy.
   - Deploy order: Cloud Functions before rules — satisfied, functions were live ahead of the rules change.
   - Real client flows (iOS `JoinCommitmentView`/`FirebaseInvitationRepository`, Android `JoinCommitmentViewModel`/`FirebaseInvitationRepository`) were compile-checked but not run against a live/emulator backend — the emulator verification used hand-written JS clients matching the rule shape, not the actual app repos. Functional (not security) risk; worth a manual pass on both platforms before shipping.
   - Minor, noted for later: `acceptGroupInvitation` is now optimistic (no poll) — if the inviter left the group between send and accept, the CF silently refuses and the client has already shown success / created a local commitment. The "X joined" notification also still fires in that case. Group-link poll only checks for `"completed"`, never surfaces `"failed"` distinctly (reads as the generic "still pending" timeout instead) — self-heals via the `alreadyMember` retry path, so low severity.
3. **Security: photo encryption defeated for any signed-in user.** **Reframed 2026-07-18 — no longer "any account holder can decrypt any proof photo."** Completions are still readable by all authenticated users (carrying `uploaderEncryptionKey`), and `users/{userId}` is still readable by all authenticated users (carrying `imageEncryptionKey`, used as a fallback source for the same key — see `GroupDetailView.swift:1189`, `getUser(id: uploaderID)` called unscoped to group membership). But the encrypted *blob* itself is now gated by `storage.rules` (deployed as part of must-fix #4): reading a key without Storage access to the matching blob decrypts nothing. Remaining exposure is real but narrower — a stranger can still learn *that a key exists* and, combined with a leaked/guessed Storage path, decrypt a photo they can otherwise access; and the `imageEncryptionKey`/`email`/`fcmToken` overexposure on `users` is worth closing regardless (see #7). **Not fixed, now correctly lower-priority (defense-in-depth, not a live "any photo, any user" hole):** scoping completions reads to group members needs a client-side query redesign first — `FirebaseCompletionRepository.getCompletionsForUsers()` (both platforms) queries by a flat `whereIn("userID", chunk)` across all of a user's group-mates with no `groupID` filter (every call site already has the relevant `groupID`(s) in scope, though — see `getGroupCompletions`/`getCompletions(groupID)`, an existing correctly-scoped sibling query already used by the group detail screen on both platforms as the template). Deferred; revisit after #7.
4. **Security: no Storage rules in repo.** **FIXED 2026-07-05, DEPLOYED 2026-07-18** (iOS repo commit `36701c6`). Added `storage.rules` scoped to actual paths in use on both platforms (`proofs/{userID}/{commitmentID}/...`, `profile-photos/{userID}/...`), wired into `firebase.json`. Proof photos: readable by uploader or group member of that *specific* commitment's group (`isGroupMemberOfCommitment`, Firestore lookup), solo stays owner-only. Profile photos: readable by any signed-in user, writable by owner only. **Live rules before this deploy were the wide-open default template** (confirmed with the user, not independently verifiable from this environment) — i.e. any authenticated user could read/write any Storage object. This was the actual live exposure behind must-fix #3 (any signed-in user could decrypt any proof photo): the `uploaderEncryptionKey`/`imageEncryptionKey` fields being readable doesn't matter if the encrypted blob itself is also readable by anyone. Deploying this rules file closes that — a stranger with a key still can't fetch a blob outside their own group, and a member of group G can't fetch group H's blob. `firebase deploy --only storage` completed successfully.
5. **Security: Android backup wide open.** **FIXED 2026-07-05** (Android repo commit `f64e735`). `tinyact_encryption_keys.xml` (holds per-user/group proof-photo decryption keys) now excluded from both `data_extraction_rules.xml` (API 31+) and `backup_rules.xml` (legacy). Everything else still backs up as before.
6. **User search broken at scale.** **FIXED 2026-07-08** (Android `bfee21e`, iOS `05d6be7`, both built/compiled green). `username` search now uses an indexed Firestore prefix range query (`orderBy`/`startAt`/`endAt`) instead of a `limit(50)` scan — scales to any collection size. firstName/lastName still fall back to the old bounded scan when the username prefix misses (no lowercase mirror field exists for them yet) — same limitation as before, not a regression, not full-text search. iOS had the identical bug (its own code comment named the fix); fixed on both platforms to keep parity.
7. **`users` collection readable by all authed users** — audit which fields are exposed (email, fcmToken?); consider splitting public/private profile docs.
